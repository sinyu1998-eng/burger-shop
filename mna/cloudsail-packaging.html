CloudSail · Fideight — Packaging Review

包装与整合方案

2026-11-19 ｜ 基于仓库现状（15 个公开页面 + 闭源 private/）｜ Carol Huang

一、核心判断

这个项目的内容已经足够，问题不在缺页面，而在三类内容混在一起：客户看的、投资人看的、内部推演用的，全部平铺在同一层。结果是每一类读者都要自己筛，筛不动就走了。

页面实际读者当前状态
index / product / tech / cockpit客户正确
articles / contact客户正确
bp / deck / seed / crowdfund投资人不该公开并列
competitors内部不该公开
prototype / glasses技术评估者需收进二级
ru / pay俄区客户应做成区域变体

最关键的一条：把 BP、Deck、竞品分析公开挂在客户官网上，等于把底牌摊给竞争对手看，同时也让客户看到「这家还在融资」，削弱成交信心。

二、整合后的结构

CloudSail ├── / 首页（一句话 + 三条证据 + 一个 CTA） ├── /product 产品：工厂只发货，其余我们托管 │ ├── /cockpit 驾驶舱演示（可交互） │ └── /tech 技术架构 ├── /cases 客户案例 ← 目前缺失，M&A 商城可直接做第一个 ├── /articles 专栏（履约九态） ├── /contact 联系 ├── /ru 俄区版本（语言变体，不是独立站） └── /investors ← 投资人区，加密码或仅发链接，不进导航 ├── bp / deck / seed / crowdfund / competitors

原则：客户路径只有五步——首页 → 产品 → 案例 → 技术 → 联系。任何不服务这条路径的内容，退出导航。

三、五个具体问题

P0融资材料公开暴露

bp.html / deck.html / seed.html / crowdfund.html / competitors.html 五个页面现在公开可访问，且很可能被搜索引擎收录。建议：移入 /investors，加 HTTP Basic Auth 或改用不可猜的 URL；同时在 robots.txt 中屏蔽。

P0缺案例页

官网说了「工厂只需要发货」，但没有一个真实客户证明这件事。你手上的 M&A 商城（77 个文件已上线）就是现成的第一个案例。没有案例的 B2B 官网，转化率会低一半以上。

P1缺报价与交付周期

客户看完 product 页，最想知道两个数字：多少钱、多久能上。现在两样都没有，只能去联系页问，中间流失一大半。建议放三档套餐（试点 / 标准 / 全托管），哪怕只写「起步价」。你给爱造软件的方案里已有价格带（托管年费 1.2–3.6 万 + 实施 3–8 万），可以直接用。

P1俄区是独立站，不是语言层

ru.html 与 pay.html 自成一套，和主站没有互链。要么做成语言切换（右上角 RU），要么明确标为「俄罗斯专区」并给出为什么单独计费。现在这种状态，访客会以为进错了站点。

P2导航缺失

15 个页面各自引用 style.css，但没有统一头部导航和页脚。用户从搜索引擎落在任意一页，都找不到回主站的路径。这是最便宜也最有效的修复。

四、和 M&A 的整合

两者不是并列产品，是「系统 + 样板」的关系：

角色M&ACloudSail
本质自营品牌，验证选品与销售把验证过的流程产品化，卖给工厂
对外产品库（买家看货）系统（工厂看能力）
关系M&A 跑通 = CloudSail 的案例；CloudSail 卖出去 = M&A 的低成本履约通道

具体做法：在 CloudSail 加一页 /cases/marguerite-asbury，写清楚「一个义乌品牌，如何在不雇运营的情况下把货卖到 34 个国家」。用真实数据，不用形容词。

五、和 Sean 的 tradoncorps 怎么接

他说这是个 B2B 外贸平台，你觉得「相对简单」——我同意一半。

简单在：撮合类平台的 MVP 确实轻，买卖双方 + 询盘 + 商品展示，两三个月能跑。

难在：撮合之后的履约没人管，而履约正是你的强项。所以你们不是竞争，是上下游。

层谁做产出
流量与撮合Sean 的 tradoncorps买家、询盘、订单
履约与托管CloudSail验厂、打样、生产跟踪、拼柜、单证
样品与选品M&A 产品库可售 SKU 与真实报价

接口只需要四个：

  1. 订单对象：订单号、买家、SKU、数量、目标价、目的港
  2. 履约状态回写：把「履约九态」的当前状态推回他的平台，买家能看到进度
  3. 报价请求：他从平台发起询价，你回一个带有效期的报价
  4. 单证回传：发票、装箱单、提单号

这四条用最朴素的方式实现即可（Webhook + JSON），不用一开始就谈 API 规范。先把第一单跑通，接口形态自然会收敛。
